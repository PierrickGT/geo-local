Lattice — Implementation Plan

v0.1 · draft 6-week Phase 1 2–3 engineers ~38 tickets

Lattice is a knowledge-graph editor for GRC20 / Geo. Users browse entities, inspect their typed properties and relations, and propose changes — individually or in batches — that get signed and published on-chain. This document is the engineering plan to get the Graphite design direction from mockup to shipped Phase 1.

Entities / list

What ships in Phase 1

  • Entities list — virtualized table, filter, multi-select, bulk actions.
  • Entity detail — identity, types, properties, incoming/outgoing relations.
  • Create & edit forms — typed property editing, staged as pending edits.
  • Edit queue — pending changes with diffs; batched publish as a single on-chain transaction.
  • Global search — by name, property value, and full 32-char id.
  • Graph view — React Flow canvas with node inspector (basic, not force-clustered).
  • Wallet auth — wagmi + RainbowKit, sign edits on publish.

What is explicitly not in Phase 1

  • Realtime collab / streaming others' edits (Phase 2).
  • Conflict resolution beyond last-write-wins on publish failure.
  • Rich-text descriptions, file/image properties, embedded media.
  • PR-style review workflow. Edits are solo-authored then published.
  • Large-graph rendering beyond ~500 visible nodes.
→ Guiding principle

The core user loop is browse → stage → publish. Every screen should make the current state of that loop legible — how many edits are pending, what will change, what's already on-chain.

02 · Design principles

Optimistic first, authoritative eventually

Every edit is applied locally the moment the user makes it. The on-chain state is the source of truth; the local cache reconciles against it. This keeps the UI feeling instant even though publishes take seconds.

Edits are first-class objects

A pending change is not a dirty form field — it's a record in a queue, with an author, a timestamp, a diff, and a stable id. This lets us show them in the Edits tab, revert individually, and batch-publish.

Deep-linkable everything

Every entity, every edit, every graph view is a URL. /e/021ccf86…, /edits/3a2b, /graph?focus=021ccf86…. No modal-only state.

Keyboard parity with pointer

⌘K palette, j/k row navigation, e to edit, ⌘↵ to save, g d go detail. Developer-tool aesthetic demands developer-tool ergonomics.

Fail loud, recover cheap

On-chain writes fail. Show the user exactly which edit failed, why, and a one-click retry. Never silently drop a staged edit.

04 · Data model & GRC20 mapping

GRC20 is triple-based: every fact is (entity, property, value). Our UI surfaces this as entities with bags of typed properties and directed relations. The client type system mirrors the protocol closely so the publish step is mostly serialization.

Core types

type EntityId = string;   // 32-char hex (no 0x prefix)
type PropertyId = string; // 32-char hex

type DataType =
  | 'text' | 'number' | 'checkbox'
  | 'url' | 'time' | 'point'
  | 'relation';

interface Entity {
  id: EntityId;
  name: string;          // resolved via Name property
  description?: string;
  types: EntityId[];      // classifying type entities
  properties: PropertyValue[];
  relations: Relation[];   // outgoing only; incoming resolved by reverse query
  space: string;
  cover?: string;         // Phase 2
}

interface PropertyValue {
  propertyId: PropertyId;
  propertyName: string;   // denormalized for display
  dataType: DataType;
  value: string | number | boolean | Date;
  language?: string;      // e.g. 'en' for text
}

interface Relation {
  id: string;
  typeId: PropertyId;     // 'has property', 'subclass of', etc
  toEntityId: EntityId;
  toEntityName: string;
}

Edit type — the central abstraction

type Edit =
  | { kind: 'entity.create'; id: string; name: string; description?: string; types: EntityId[]; properties: PropertyValue[] }
  | { kind: 'entity.update'; entityId: EntityId; field: 'name'|'description'; before: string; after: string }
  | { kind: 'property.set';   entityId: EntityId; propertyId: PropertyId; dataType: DataType; before?: any; after: any }
  | { kind: 'property.unset'; entityId: EntityId; propertyId: PropertyId; before: any }
  | { kind: 'relation.add';   fromId: EntityId; typeId: PropertyId; toId: EntityId }
  | { kind: 'relation.remove'; relationId: string; fromId: EntityId; typeId: PropertyId; toId: EntityId };

interface PendingEdit {
  id: string;              // local uuid
  edit: Edit;
  createdAt: number;
  author: `0x${string}`;   // wallet address
  status: 'staged' | 'publishing' | 'published' | 'failed';
  txHash?: `0x${string}`;
  error?: string;
}

Mapping to on-chain ops

entity.createFan-out: setName + N × setTriple + N × addTypeOne call per property. Batched via multicall.
property.setsetTriple(entity, property, value)Overwrites existing triple silently; we derive before from cache for diff display.
property.unsetdeleteTriple(entity, property)—
relation.addaddRelation(from, type, to)—
relation.removeremoveRelation(id)—

⚠ Assumption to verify

This mapping assumes GRC20's Space contract exposes a multicall-compatible batch entry point. If it doesn't, we either (a) submit N transactions sequentially with a progress indicator, or (b) deploy a thin forwarder contract ourselves. W1 spike confirms before locking the edit-queue design.

Indexer query shape (GraphQL)

# List with filter/sort/pagination
query Entities($space: String!, $first: Int, $after: String, $search: String) {
  entities(space: $space, first: $first, after: $after, search: $search) {
    pageInfo { endCursor hasNextPage }
    edges { node { id name description types { id name } } }
  }
}

# Full detail — properties + outgoing + incoming relations
query Entity($id: ID!) {
  entity(id: $id) {
    id name description types { id name }
    properties { propertyId propertyName dataType value }
    outgoing: relations { id type { id name } to { id name } }
    incoming: backlinks { id type { id name } from { id name } }
  }
}

05 · Edit queue & publish flow

This is the trickiest part of the app and where most of the bugs will live. Spec it carefully.

State machine

// Per-edit lifecycle
staged      // in queue, not yet submitted
  → publishing  // included in an in-flight tx
  → published   // tx confirmed; reconciled against indexer
  → failed      // tx reverted OR indexer didn't reflect it within 60s

// Queue-level state
idle → publishing → (idle | partially-failed)

The publish algorithm

  1. User clicks Publish N changes on the Edits page.
  2. We snapshot the current queue — later edits to any of those records don't affect the in-flight batch.
  3. Each edit is encoded into a contract call via lib/grc20/encode.ts.
  4. Calls are aggregated into a single multicall (or submitted sequentially if unsupported — see W1 spike).
  5. Wallet signs; we surface "waiting for signature" state with a cancel option.
  6. On tx hash received, all snapshotted edits move to publishing, persisted with txHash.
  7. We watch the tx via viem's waitForTransactionReceipt; on success, we don't mark edits published yet.
  8. We poll the indexer with an exponential backoff until the new state is reflected (or 60s timeout).
  9. On reflection, edits move to published and drop from the pending queue into history.
  10. On timeout or tx revert: edits move to failed, remain in queue, show the error inline with a Retry action.
→ Why the indexer-poll step

Tx confirmation is not the same as data visibility. If we mark edits published when the tx confirms, the user's next list refresh may still show stale data and they'll think they hallucinated the change. Wait for the indexer to catch up before declaring victory.

Persistence

Queue state lives in zustand with an idb-keyval adapter. Key design points:

  • Survives hard reload — the user never loses work.
  • Keyed by {walletAddress}:{spaceId} so switching accounts doesn't leak edits.
  • On wallet-disconnect, queue stays in IDB but UI locks.
  • On publish success, entries migrate from "pending" to a bounded "history" bucket (keep last 200).

Optimistic UI rule

Every read selector (useEntity, useEntities, search) composes indexer data + pending edits for that entity. A component never asks "is this published?" — it asks "what does this entity look like right now from my perspective?" and gets one answer.

function useEntity(id: EntityId) {
  const remote = useQuery(...);
  const pending = useEditQueue(s => s.pendingFor(id));
  return useMemo(() => applyEdits(remote.data, pending), [remote.data, pending]);
}

Concurrency edge cases we will hit

  • Two sessions, same wallet. Both queues diverge. Mitigation: on focus, re-read IDB; last write wins per edit-id.
  • Edit references an entity that gets deleted on-chain. On publish failure, surface "target no longer exists" with the option to remove the edit.
  • User edits a property, then another user publishes a different value first. Our edit still applies and overwrites — this is WYSIWYG; the diff shown to them at publish time uses the cached "before" from when they started editing. Acceptable for Phase 1.

07 · Performance & scale

Entities list at 10k+

  • Row virtualization via react-virtual (viewport + 10 overscan).
  • Indexer pagination in 200-row pages; TanStack Query infinite query.
  • Sort and type-filter pushed to the indexer, not client-side.
  • Search (name/id) debounced 150ms, cancels in-flight.
  • Target: first meaningful paint < 600ms on a warm cache, 60fps scrolling.

Graph at scale

React Flow degrades past ~500 visible nodes. Strategy:

  • Default view: only the focused entity + direct neighbors (< 30 nodes). No "load the whole space".
  • "Expand" action on a node adds its neighbors; counter shows total visible nodes with a soft cap at 300.
  • Beyond 300, prompt user to narrow focus or switch to list view.
  • Phase 2 if needed: Sigma.js backend with WebGL for true large-graph.

Required E2E flows

  1. Browse list → filter by type → open entity → scroll properties.
  2. Search by id → open result → verify properties match.
  3. Create new entity with 2 properties → see it in pending queue → publish → see on-chain → list reflects.
  4. Edit an existing property → stage → see diff on Edits page → revert one edit → publish remaining.
  5. Add a relation → publish → verify incoming shows on target.
  6. Stage 3 edits → lose internet → hard-reload → queue survives → reconnect → publish.
  7. Publish that fails → retry → succeeds.

E2E runs against a local Anvil node seeded with a fixture space, so tests are deterministic and free.

11 · Risks & open questions

High

GRC20 batch semantics are unclear

We've assumed multicall-style batching. If it's not supported, every edit is a separate signed tx — terrible UX for a 10-edit publish.

Mitigation: W1 spike (LAT-013) resolves this in week one. Fallback: ship sequential with per-edit progress, investigate forwarder contract in Phase 1.5.
High

Indexer lag creates "did my edit land?" confusion

Tx confirms in 2s; indexer may take 15-60s. Users will refresh and see stale data and think publish failed.

Mitigation: Optimistic rendering from the edit queue means the user never sees stale data as long as the queue knows about the edit. Publish bar shows "waiting for indexer" phase distinct from "waiting for tx".
Medium

Schema drift — new dataType added by protocol

If GRC20 adds a new dataType (e.g. markdown), our PropertyEditor crashes on unknowns.

Mitigation: PropertyEditor falls back to a raw-text editor with a "Unsupported type — advanced" warning. Never crash.
Medium

Large graphs overwhelm React Flow

Users may load spaces with thousands of entities and try to view the whole graph.

Mitigation: Never default to whole-space view. Soft cap at 300 nodes with clear "narrow focus" CTA. Sigma.js is a Phase 2 option.
Medium

Wallet UX friction on every publish

If every publish requires a signature prompt + gas, users rage-quit.

Mitigation: Encourage batching (publish bar says "3 changes · 1 signature"). Investigate session keys / smart wallets in Phase 2.
Low

Name collisions — two entities with same name

Display is ambiguous.

Mitigation: When duplicates detected in a result set, append disambiguator (first 6 chars of id) in mono font.

Open questions for product

  • Spaces — does the UI need a space switcher, or is there one space per deployment?
  • Permissions — can anyone with a wallet stage+publish, or does the space contract gate writers?
  • Rollback — if a published edit was wrong, do we offer a "revert published edit" flow, or is that a user-owned operation (make a new inverse edit)?
  • Descriptions — plain text only, or Markdown? Materially changes the editor and detail view.
  • Images / files — are any properties binary in Phase 1, or can we defer to Phase 2?

12 · Phase 2+ parking lot

Explicitly out of Phase 1, tracked here so they don't get lost.

  • Realtime collab — subscribe to indexer, stream others' published edits into list/detail without refresh.
  • Session keys / smart wallets — publish N edits without N signatures.
  • Rich descriptions — Markdown editor, embedded links to other entities.
  • Binary properties — images, files, via IPFS.
  • PR-style review — propose edits that a space admin approves before on-chain publish.
  • Large-graph mode — Sigma.js + WebGL for 10k-node views.
  • Visual regression testing — Percy or Chromatic once UI stabilizes.
  • Bulk import — CSV → staged edits.
  • Schema-aware autocomplete — property suggestions based on declared types.
  • Graph queries — "all entities of type X with property Y > Z".
  • Activity feed — per-entity timeline of edits (who / when / what).
  • Mobile — read-only first, then a tighter edit experience.
